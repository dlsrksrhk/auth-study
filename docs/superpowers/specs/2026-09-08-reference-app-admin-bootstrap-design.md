# Reference App Task 3: 최초 관리자 bootstrap 설계

작성일: 2026-09-08

상태: 대화에서 후보 자격, 조율 서비스 분리, 실패 처리와 검증 범위 승인 완료. 문서 검토 후 구현 계획을 작성합니다.

## 목적과 작업 범위

검증된 외부 로그인 정보를 이용해 독립 Reference App의 최초 로컬 관리자 한 명을 지정합니다. 이는 OAuth/OIDC 프로토콜 자체가 아니라 앱의 초기 권한 정책입니다.

상위 계획은 [Reference App 구현 계획](../plans/2026-08-21-oauth-oidc-reference-app.md)의 Task 3입니다. 선행 [Task 2 설계](2026-09-08-reference-app-user-provisioning-design.md)와 사용자 프로비저닝 구현을 재사용합니다. 기반 커밋은 `09f2f86`이며, 이 시점에 사용자 생성·사본 갱신과 bootstrap singleton 스키마가 준비되어 있습니다.

이번 작업은 bootstrap 도메인·저장 어댑터·정책 서비스·상위 조율 서비스와 실제 PostgreSQL 검증까지입니다. 로그인 엔드포인트·토큰 검증·세션 발급은 Tasks 4–5, 관리자 변경 API와 마지막 관리자 보호는 Task 7입니다. 관리자 복구/reset 기능, 운영용 자동 계정 승격, SPA는 추가하지 않습니다.

## 후보 자격과 일회성 정책

다음 조건을 모두 만족하는 현재 사용자를 최초 관리자 후보로 인정합니다.

- 앱 전체 bootstrap 상태가 미완료입니다.
- 사용자 생성·갱신 후 로컬 상태가 `ACTIVE`입니다.
- 이번 호출에서 검증된 외부 정보의 HR 역할 집합에 정확히 `COMPANY_ADMIN`이 있습니다.

권한 판단에 과거 사본, 이메일, 브라우저 입력 또는 IdP 내부 숫자 ID를 사용하지 않습니다. 검증된 issuer/subject와 claim만 입력받고, issuer 신뢰 및 토큰 검증은 후속 로그인 계층이 담당합니다.

`DISABLED` 사용자에게는 APP_ADMIN을 추가하거나 ACTIVE로 바꾸지 않습니다. 해당 사용자는 bootstrap 기회를 소비하지 않으며, 외부 사본 갱신은 기존 Task 2 정책대로 처리합니다. 실제 앱 접근 거절은 후속 로그인 계층의 책임입니다.

최초 호출에서 자격이 없었던 사용자도, bootstrap 미완료 상태에서 이후 로그인 시 자격을 충족하면 후보가 될 수 있습니다. 계정 생성이 최초인 사용자로 제한하지 않습니다.

지정 성공 시 기존 `APP_USER`를 유지하고 `APP_ADMIN`을 추가합니다. 완료 상태에는 로컬 사용자 UUID와 완료 시각을 기록합니다. 앱 전체 singleton이므로 회사별 또는 issuer별로 각각 지정하지 않습니다.

완료 여부는 관리자 수를 매번 세어서 판정하지 않고 bootstrap 완료 기록으로 판정합니다. 완료 후 다른 COMPANY_ADMIN이 로그인하거나 기존 관리자의 외부 HR 역할이 사라져도 자동 승격·강등하지 않습니다. 기존 관리자가 비활성화되거나 앱 역할을 변경하더라도 bootstrap을 다시 열지 않습니다.

## 구조 선택과 책임

기존 프로비저닝 서비스에 모든 정책을 넣는 대신 상위 조율 서비스를 별도로 둡니다. 파일은 늘지만 사용자 사본 동기화와 초기 권한 정책을 분리할 수 있습니다.

| 구성 요소 | 책임 |
|---|---|
| `AppLoginProvisioningService` | 검증된 입력을 받아 bootstrap 잠금, 기존 JIT 호출, 관리자 지정, 최신 결과 반환을 하나의 트랜잭션으로 조율 |
| 기존 `AppUserProvisioningService` | 사용자 생성·외부 정보 갱신만 수행하며 상위 트랜잭션에 참여 |
| `AppAdminBootstrapService` | 잠근 bootstrap 상태와 현재 로컬 사용자를 기준으로 후보 자격 및 일회성 지정 수행 |
| `AppBootstrapState` | 미완료/완료 상태와 로컬 관리자 UUID·시각의 불변 완료 규칙 표현 |
| `AppBootstrapStateRepository` 및 JPA 어댑터 | singleton 잠금 조회와 완료 기록 저장 |
| 기존 `AppUser`·저장 port/어댑터 확장 | 로컬 APP_ADMIN 추가를 저장하고 최신 version/역할을 반환 |

상위 계획은 이미 생성된 사용자와 HR 역할을 bootstrap 서비스가 받는다고 표현하지만, 잠금을 JIT보다 먼저 얻어야 합니다. 이를 명확하게 하기 위해 조율 서비스가 **미리 singleton을 잠근 뒤** JIT와 bootstrap 정책을 순서대로 호출합니다. JIT를 먼저 별도 커밋하고 나중에 bootstrap하는 호출은 사용하지 않습니다.

## 데이터 흐름과 트랜잭션

조율 진입점은 검증된 `ExternalIdentityProfile`을 받고, 최종 `AppUserView`를 반환합니다. 후속 로그인 연결은 이 조율 진입점을 사용해야 합니다.

1. READ_COMMITTED 트랜잭션을 시작하거나 동일 계약의 상위 트랜잭션에 참여합니다.
2. `app_bootstrap_state` singleton을 잠금 조회합니다. 누락이면 오류로 중단합니다.
3. Task 2 프로비저닝으로 로컬 사용자를 생성하거나 외부 사본을 갱신합니다.
4. 잠근 bootstrap 상태와 현재 사용자의 자격을 검사합니다.
5. 조건 충족 시 APP_ADMIN 추가 및 완료 사용자 UUID·시각을 저장합니다.
6. 역할·상태·버전까지 최신인 사용자 결과를 반환하고 함께 커밋합니다.

모든 경로에서 잠금 순서는 **bootstrap_state → app_user**입니다. 개별 bootstrap/JIT 저장에 REQUIRES_NEW를 사용하지 않습니다. 외부 트랜잭션 안에서 호출되었다면 최종 성공은 그 외부 트랜잭션의 커밋까지 포함합니다.

동시 후보 중 “최초”는 요청 도착 시각이나 UUID 순서가 아니라, singleton 잠금을 얻고 후보 조건을 충족하여 최종 커밋한 사용자입니다. 앞선 후보가 롤백되면 완료 기록과 권한 부여가 남지 않으므로 다음 후보가 지정될 수 있습니다.

완료된 경우에도 이번 단계에서는 동일한 잠금 순서로 처리합니다. 캐시 기반 완료 판정이나 잠금 생략 최적화는 추가하지 않습니다. 이 선택은 조율 호출을 singleton에서 직렬화하는 비용이 있지만, 학습용 앱의 단순하고 검증 가능한 일관성을 우선합니다.

외부 정보 조회나 토큰 검증 같은 네트워크 작업은 이 트랜잭션 전에 완료되어야 합니다. 트랜잭션 안에서 IdP를 호출하지 않습니다.

## 저장과 실패 처리

기존 V1의 `app_bootstrap_state`와 최초 singleton 행을 재사용합니다. 이번 정책에는 스키마 변경이 필요하지 않으며, 적용된 V1을 다시 쓰지 않습니다.

- 미완료 상태는 지정 사용자 UUID와 시각이 모두 null입니다.
- 완료 상태는 두 값이 모두 존재하며 다른 사용자로 덮어쓰거나 초기화하지 않습니다.
- 상태 행이 없으면 임의로 생성하거나 “아직 미완료”로 간주하지 않습니다. 저장 구성 오류로 명확히 실패합니다.
- 후보 미충족은 오류가 아닙니다. 기존 역할의 사용자 결과를 반환하고 bootstrap 미완료를 유지합니다.
- 사용자 저장·역할 부여·완료 기록 저장 중 하나라도 실패하면 해당 트랜잭션 전체를 롤백합니다. 신규 계정뿐 아니라 기존 사용자의 사본·기록·version 변경도 원복됩니다.
- APP_ADMIN 저장은 다른 로컬 역할과 상태, 외부 사본 및 identity를 덮어쓰지 않습니다. 역할 변경의 version과 수정 시각은 저장 결과에 반영합니다.
- 예외를 삼키고 성공으로 반환하거나 무한 재시도하지 않습니다. HTTP 상태 코드 매핑은 이번 범위가 아닙니다.

## 검증 기준

도메인 단위 테스트와 기존 전용 PostgreSQL Testcontainers 기반 통합 테스트를 사용합니다. 실패 주입과 상태 초기화는 테스트 DB에만 적용합니다.

1. ACTIVE + 현재 COMPANY_ADMIN 후보는 APP_USER를 유지한 채 APP_ADMIN이 되고, 완료 기록이 해당 UUID를 가리킵니다. 반환 결과에도 최종 역할·version이 반영됩니다.
2. COMPANY_ADMIN이 없는 사용자 및 HR 역할이 비어 있는 사용자는 기회를 소비하지 않습니다. 이후 적격 후보는 지정될 수 있습니다.
3. DISABLED + COMPANY_ADMIN은 승격·활성화되지 않고 미완료를 유지합니다. 이후 ACTIVE 후보는 지정될 수 있습니다.
4. 기존 로컬 사용자도 현재 자격을 충족하면 최초 관리자 후보가 됩니다.
5. 서로 다른 적격 후보가 동시에 호출되어도 최초 APP_ADMIN은 정확히 한 명이고 완료 기록과 일치합니다. barrier 호출뿐 아니라 실제 DB 잠금 대기도 확인합니다.
6. 동일 identity의 동시 호출은 사용자와 기본 역할을 중복 생성하지 않고, APP_ADMIN과 bootstrap 기록도 한 벌로 수렴합니다.
7. 먼저 잠근 후보가 실패하면 그 후보의 변경이 롤백되고, 기다리던 다른 후보가 지정될 수 있습니다.
8. 역할 저장 실패 및 완료 기록 저장 실패를 주입하여 신규/기존 사용자의 전체 변경이 원복되는지 fresh DB 조회로 확인합니다. 실패 설정 자체의 오류가 기대한 실패로 통과하지 않게 구체적인 원인을 단언합니다.
9. 외부 트랜잭션에서 조율 호출 후 오류가 발생해도 JIT·역할·bootstrap 변경이 모두 롤백됩니다.
10. 완료 후 다른 후보는 자동 승격되지 않습니다. 최초 관리자의 외부 COMPANY_ADMIN 제거는 로컬 APP_ADMIN에 영향을 주지 않습니다.
11. 테스트용 로컬 정책 변경으로 최초 관리자를 비활성화하거나 APP_ADMIN을 제거해도 bootstrap 완료 기록은 유지되고 새 후보를 자동 지정하지 않습니다. 실제 관리 API나 마지막 관리자 보호 기능을 구현하는 테스트는 아닙니다.
12. singleton이 없으면 실패하고 사용자 생성·갱신이 발생하지 않습니다. 테스트 후 상태는 격리·복구합니다.
13. 기존 Task 2 회귀 테스트와 독립 backend 전체 테스트가 통과하고, IdP 코드·DB 의존 및 토큰 저장이 추가되지 않습니다.

## 다음 단계

사용자가 문서를 검토한 뒤 Task 3 전용 구현 계획을 작성합니다. 구현 계획에는 조율 서비스와 기존 사용자 저장 port 확장을 명시하여 상위 계획의 파일 목록을 보완합니다. 이번 문서 확정은 코드 구현, main 병합 또는 원격 push를 포함하지 않습니다.
