# Reference App Task 2: 로컬 사용자 JIT 프로비저닝 설계

작성일: 2026-09-08

상태: 대화에서 설계 승인 완료. 문서 검토 후 구현 계획을 작성합니다.

## 목적과 범위

독립 Reference App이 검증된 외부 로그인 정보를 받아 자체 사용자를 최초 생성하거나 갱신합니다. JIT(Just-in-Time)는 미리 계정을 등록하지 않고 최초 로그인 시 로컬 계정을 만드는 방식입니다.

상위 계획은 [Reference App 구현 계획](../plans/2026-08-21-oauth-oidc-reference-app.md)의 Task 2입니다. 이 문서는 해당 작업의 정책과 검증 기준을 구체화합니다. Task 1의 독립 Spring Boot/전용 PostgreSQL 구성을 사용하며 IdP 코드, 엔티티, 저장소, DB를 공유하지 않습니다.

이번 작업은 스키마, 사용자 도메인, 저장 어댑터, 프로비저닝 서비스와 테스트까지입니다. OAuth/OIDC 통신·토큰 검증·세션 발급은 Tasks 4–5, 최초 관리자 지정은 Task 3, 관리 API는 Task 7에서 구현합니다. 실제 브라우저 상호운용성 검증은 Task 10입니다.

## 확정된 접근

도메인 모델과 JPA 저장 모델을 분리합니다. JPA 엔티티 중심 통합보다 파일은 늘지만 사용자 정책과 DB 처리의 책임을 따로 이해하고 검증하기 좋습니다.

- `AppUser`: 로컬 사용자 생성과 외부 정보 교체 규칙을 담당합니다.
- `AppUserStatus`, `AppRole`: 앱 자체 상태와 권한을 표현합니다.
- `AppUserRepository`: 도메인 관점의 저장 인터페이스입니다.
- `ExternalIdentityProfile`: 상위 로그인 계층에서 검증·선별한 외부 정보를 받습니다.
- `AppUserProvisioningService`: 입력 확인, 사용자 조회·생성·갱신과 트랜잭션을 조율합니다.
- `AppUserView`: 로컬 식별자, 외부 정보 사본, 앱 상태·역할과 기록을 반환하는 불변 결과입니다. 인증 토큰은 포함하지 않습니다.
- `AppUserJpaEntity`, `AppUserJpaRepository`, `AppUserRepositoryAdapter`: 전용 DB 매핑과 동시성 처리를 담당합니다.

## 식별과 외부 정보 정책

사용자의 로컬 식별자는 앱에서 생성한 UUID입니다. 외부 사용자 식별키는 `(issuer, subject)`이며 DB 고유 제약을 둡니다. 이메일은 식별키가 아니고 중복을 허용합니다. 이메일이 같아도 외부 식별키가 다르면 별개 사용자입니다. 자동 계정 연결은 하지 않습니다.

issuer와 subject는 검증된 값을 보존하며 임의의 대소문자 변환, 공백 제거, URI 정규화로 서로 다른 식별값을 합치지 않습니다. 필수 식별값이 없거나 유효하지 않으면 저장 전에 거절합니다. 신뢰할 issuer인지와 토큰의 진위 판정은 상위 로그인 계층의 책임입니다.

입력은 상위 계획의 `ExternalIdentityProfile` 계약을 따릅니다: issuer(URI), subject, email, displayName, company/organization(Map), hrRoles(Set). 객체는 불변으로 다루며 중첩 자료구조도 호출자의 후속 변경으로 저장할 값이 달라지지 않도록 복사합니다.

| 데이터 | 최초 생성 | 이후 프로비저닝 |
|---|---|---|
| UUID, issuer, subject | 새 UUID와 외부 식별값 저장 | 유지 |
| 이름, 이메일, 회사, 조직, HR 역할 | 제공된 정보 사본 저장 | 최신 입력으로 전체 교체 |
| 로컬 상태 | ACTIVE | 기존 값 보존 |
| 로컬 역할 | APP_USER | 기존 값 보존 |
| 생성 시각 | 현재 시각 | 유지 |
| 수정·마지막 로그인 시각 | 현재 시각 | 성공한 프로비저닝 시각으로 갱신 |
| version | 초기 버전 | 저장 변경에 맞춰 증가 |

선택 정보의 누락은 이전 사본을 제거한다는 의미입니다. 이름·이메일·회사·조직의 부재는 null, HR 역할의 부재는 빈 집합으로 표현합니다. 과거 사본을 누적하거나 부분 병합하지 않습니다. 마지막 로그인 시각은 이 작업에서 검증된 로그인 정보를 성공적으로 반영한 시각이며, 세션 발급 성공 자체를 보증하는 기록은 아닙니다.

HR 역할은 외부 정보 사본이지 앱 권한이 아닙니다. COMPANY_ADMIN이 들어와도 Task 2는 APP_ADMIN을 부여하지 않습니다. 기존 DISABLED 사용자를 자동 활성화하거나 기존 APP_ADMIN을 제거하지 않습니다.

## 스키마

Flyway `V1__app_user.sql`에 다음 세 테이블을 만듭니다.

- `app_user`: id(UUID PK), issuer, subject, email, display_name, company_snapshot(jsonb), organization_snapshot(jsonb), hr_roles_snapshot(jsonb), status, created_at, updated_at, last_login_at, version. 필수 식별값·상태·기록·버전은 NOT NULL이고 `(issuer, subject)`는 UNIQUE입니다. email에는 UNIQUE를 두지 않습니다.
- `app_user_role`: app_user_id/role 복합 PK. 사용자 FK와 삭제 cascade를 둡니다. 기본 APP_USER 저장은 사용자 생성과 원자적으로 처리합니다.
- `app_bootstrap_state`: singleton key, bootstrapped_user_id, bootstrapped_at, version. 최초 관리자 지정 전의 singleton 행을 migration에서 준비합니다. 사용자 참조는 로컬 UUID이며 지정 ID와 시각은 함께 비어 있거나 함께 설정됩니다. 지정 로직은 Task 3에서 구현합니다.

회사·조직을 IdP 테이블의 복제본으로 만들지 않습니다. 공개 claim 계약에서 허용한 코드·이름 등의 사본만 저장합니다. 원본 UserInfo 전체를 저장하지 않으며 IdP 내부 숫자 account/user/company ID와 OAuth 토큰은 입력 계약·저장 모델·반환 모델에 포함하지 않습니다. 임의 Map이 금지 정보를 우회 저장하는 통로가 되지 않도록 공개 claim 필드를 선별합니다.

## 처리와 실패 경계

1. 상위 계층이 토큰 검증과 ID Token subject/UserInfo subject 일치를 확인합니다.
2. Task 2 서비스가 필수 식별값과 입력 구조를 확인합니다.
3. 외부 식별키로 로컬 사용자를 찾고 없으면 ACTIVE + APP_USER로 생성합니다.
4. 기존 사용자라면 외부 사본과 기록만 갱신합니다.
5. 저장 성공 후 로컬 사용자 결과를 반환합니다.

정상 응답에서 선택 claim이 빠진 경우와 외부 조회 자체가 실패한 경우를 구분합니다. 조회 실패나 검증 실패를 빈 프로필로 변환하여 전달하지 않습니다. 잘못된 입력은 저장하지 않으며 저장 중 오류는 해당 트랜잭션을 롤백합니다. 부분 사용자나 역할만 남기지 않습니다.

DISABLED의 외부 사본 갱신과 앱 이용 허용은 별개입니다. Task 2는 상태를 보존하여 반환하며, Task 5에서 해당 상태를 확인해 앱 세션 발급을 차단합니다. HTTP 오류 응답과 세션 무효화는 이번 범위가 아닙니다.

## 동시성과 후속 작업 연결

동일 식별키로 동시 최초 로그인을 수행해도 사용자와 기본 역할은 한 벌만 남고 성공한 요청들은 같은 UUID를 반환해야 합니다. 예상된 중복 생성 경쟁은 기존 행을 다시 읽고 갱신하는 방식으로 수렴시킵니다. DB 오류를 잡고 무조건 성공으로 처리하거나 무한 재시도하지 않습니다.

프로비저닝은 트랜잭션 단위로 원자적이어야 합니다. 충돌 복구는 정상적으로 사용 가능한 트랜잭션 경계에서 수행하며, 실패한 저장 작업 뒤 같은 트랜잭션을 무조건 계속 쓰는 방식에 의존하지 않습니다. 구체적인 SQL/재시도 구현은 구현 계획에서 고정하고 실제 PostgreSQL 경쟁 테스트로 증명합니다.

기존 사용자 갱신은 오래된 객체에 들어 있는 로컬 상태·역할을 DB에 덮어쓰지 않습니다. 잠금 또는 버전 충돌 감지로 관리자의 동시 변경을 보호합니다. 동시에 받은 외부 사본은 DB에서 직렬화된 갱신 순서의 최종 값으로 수렴하며, 외부 시스템의 변경 시각 순서를 추론하지 않습니다.

Task 3는 bootstrap_state → app_user 순서로 잠금을 얻고, JIT와 최초 관리자 지정을 같은 트랜잭션에서 처리해야 합니다. 따라서 이번 서비스는 상위 트랜잭션 참여가 가능해야 하며 강제 REQUIRES_NEW로 JIT만 먼저 확정하지 않습니다. Task 3 연결 시 singleton 잠금은 사용자 조회·생성·갱신보다 먼저 수행합니다. 이번 작업에서 관리자 지정 동작은 추가하지 않습니다.

## 검증 기준

도메인 단위 테스트와 전용 PostgreSQL Testcontainers 통합 테스트를 사용합니다. 데이터 초기화와 실패 주입은 테스트 DB에만 적용합니다.

1. migration 실행 및 세 테이블의 필수 제약과 bootstrap singleton 초기 상태를 확인합니다.
2. 최초 생성은 UUID, ACTIVE, APP_USER와 일관된 기록을 반환합니다.
3. 같은 issuer/subject 재로그인은 같은 UUID를 반환하고 행 수가 늘지 않습니다.
4. issuer 또는 subject가 다르면 각각 별도 사용자를 생성합니다.
5. 이메일 중복을 허용하며 이메일 변경으로 계정이 바뀌지 않습니다.
6. 외부 사본 교체와 선택 claim 누락 시 이전 값 제거를 확인합니다.
7. DISABLED와 APP_ADMIN을 포함한 기존 로컬 상태·역할은 갱신 후에도 유지됩니다.
8. 필수 식별값 오류나 잘못된 입력 구조는 DB를 변경하지 않습니다.
9. 동시 최초 생성은 같은 UUID와 한 사용자/기본 역할로 수렴합니다. 순차 호출만으로 대체하지 않습니다.
10. 기존 사용자 갱신과 로컬 상태·역할 변경의 경쟁에서도 관리자 변경이 유실되지 않습니다. 관리 API 대신 테스트용 저장 경계를 사용합니다.
11. 저장 중 실패를 주입해 사용자 생성·역할 저장 전체와 기존 사용자 갱신이 롤백되는지 확인합니다.
12. 입력 자료구조의 후속 변경이 도메인 사본을 변경하지 않으며, 금지된 내부 식별자와 토큰이 저장·반환되지 않는지 확인합니다.
13. 기존 독립 backend smoke test를 포함해 전체 backend 테스트를 실행합니다.

UserInfo subject 불일치 시 프로비저닝을 호출하지 않는 테스트는 실제 호출 계층을 만드는 Task 5에서 수행합니다. 이번 작업에서는 가짜 토큰 검증기를 추가하지 않습니다. 기존 상위 Task 2에 적힌 이 항목의 검증 위치를 여기서 명확히 합니다.

## 완료와 다음 단계

설계 문서 검토 후 Task 2에 한정한 구현 계획을 작성합니다. 구현에서는 실패 테스트 → 실패 확인 → 최소 구현 → 통과 확인 순서를 사용합니다. 완료 판단에는 실제 PostgreSQL 동시성·롤백 검증과 독립성 검사가 포함됩니다. Task 3 이후 기능, main 병합과 원격 push는 이번 설계 확정에 포함하지 않습니다.
